# Data access and regeneration

RP1 Analysis v1.2.3 is distributed with the governed inputs needed for normal
scientific analysis and repository-owned testing. A user can validate and run
the canonical analysis without downloading MODIS, VIIRS, boundary or Earth
Engine source data.

External acquisition is required only when reconstructing upstream data
products from source observations. The normal analysis path and the upstream
regeneration path are deliberately separate.

## Data availability by workflow

| Data family | Shipped in this repository | Normal analysis | Upstream regeneration |
| --- | --- | --- | --- |
| Governed consolidated ACZ and district fire panels | yes | used directly | regenerated by `RP1_Project/merge_af_ba_panels.py` if required |
| Governed ACZ/district analysis geometries and district-to-ACZ crosswalk | yes | used directly | regenerated from Stage 1 if required |
| RQ1/RQ2/RQ3 qualified analysis authorities | yes | used for validation/reference qualification | regenerated by the qualified analysis workflow when required |
| Ghana admin-0/admin-2 source geometries | yes, extracted shapefile families | not required | Stage 1 source |
| Agro-climatic-zone and agro-ecological-zone source geometries | yes | not required | Stage 1 source/reference |
| Stage 1 `unit_universe.csv` hand-off for active-fire preparation | yes | not required | Stage 2 identity input |
| Raw yearly MODIS/VIIRS FIRMS active-fire files | no | not required | obtain from NASA FIRMS and stage locally |
| Earth Engine burned-area scripts | yes | not executed | use to regenerate burned-area exports if required |
| BA-2001 and BA-2012 Earth Engine CSV export bundles | yes | not required directly | usable as merger inputs or replace with a freshly regenerated equivalent |
| Runtime `out/` trees | no | generated per run | generated by the relevant stage |

## Normal RP1 analysis

The canonical analysis consumes only repository-owned governed inputs under:

```text
RP1_Project/rp1_analysis/data/raw/
RP1_Project/rp1_analysis/data/geo/
RP1_Project/rp1_analysis/data/reference/
RP1_Project/rp1_analysis/data/authorities/
```

Validate and execute from the repository root:

```bash
python RP1_Project/rp1_analysis/scripts/validate_inputs.py
python RP1_Project/rp1_analysis/scripts/qualify_reference_methods.py
python RP1_Project/rp1_analysis/scripts/execute_notebook.py --run-id example_run
python RP1_Project/rp1_analysis/scripts/validate_run.py --run-id example_run --write-report
```

The input validator calculates hashes and sizes for the current staged files, but runtime scientific admission is controlled by the full schema/support/geometry/reconciliation/population contract. `RP1_Project/rp1_analysis/data/input_sha256.json` remains the immutable exact-byte inventory of the release: canonical files should report `PASS + MATCH`, whereas a scientifically valid reconstruction may report `PASS + DIFFERENT`. Do not edit the inventory to make regenerated bytes appear canonical.

Each run writes only below `RP1_Project/rp1_analysis/out/runs/<run_id>/` and
uses run-local publication and provenance outputs.

## Upstream source acquisition

### Ghana administrative boundaries

Source: Humanitarian Data Exchange (HDX), COD-AB GHA.

- landing page: `https://data.humdata.org/dataset/cod-ab-gha`
- expected Stage 1 families:
  `geo_data_prep/data/raw/aoi/gha_admin0.*` and
  `geo_data_prep/data/raw/districts/gha_admin2.*`

The distributed repository already contains the extracted shapefile families
used by Stage 1. A fresh upstream reconstruction may reacquire them from HDX
and should preserve the provider licence and attribution.

### Agro-climatic-zone source layer

The maintained Stage 1 source is:

```text
geo_data_prep/data/raw/zones/Agro_climatic_zone.*
```

It is based on Yamba et al. (2023), *PLOS Climate* 2(1): e0000023,
`https://doi.org/10.1371/journal.pclm.0000023`. The repository also contains
the agro-ecological-zone reference family used by the geography subproject.

### MODIS and VIIRS active-fire inputs

Raw yearly active-fire files are not distributed. For an upstream Stage 2
rebuild, obtain source files from NASA FIRMS:

- archive: `https://firms.modaps.eosdis.nasa.gov/download/`
- service information: `https://www.earthdata.nasa.gov/data/tools/firms`

Stage them using the configuration-owned locations and naming families:

```text
RP1_Project/rp1_mv_firms_panels/data/raw/modis/MODIS_<YYYY>.*
RP1_Project/rp1_mv_firms_panels/data/raw/viirs/VIIRS_<YYYY>.*
```

Stage 2 also expects ACZ and district boundary files below
`data/raw/boundaries/`; these are regeneration-time working copies and are not
part of the distributed product.

## Burned-area export resources

`RP1_Project/rp1_gee_ba_scripts/` contains the Earth Engine JavaScript source
and the two CSV export families consumed by the AF/BA merger:

```text
RP1_Project/rp1_gee_ba_scripts/RP1_Project_MODIS_BA_c1_2001/
RP1_Project/rp1_gee_ba_scripts/RP1_Project_MODIS_BA_c1_2012/
```

The shipped CSV bundles support reproducibility and upstream reconstruction.
Earth Engine itself remains an external execution service; running the scripts
is not part of normal RP1 analysis or the Python test estate.

## Rebuilding the consolidated analysis inputs

A full upstream reconstruction consists of:

1. Stage 1 geography preparation with `geo_data_prep`.
2. Stage 2 active-fire panel generation with locally acquired FIRMS inputs.
3. Burned-area export generation in Earth Engine, or use of the governed
   shipped export bundles.
4. AF/BA consolidation with `RP1_Project/merge_af_ba_panels.py`.
5. Validation of the regenerated analysis inputs before scientific execution.

The merger is an input-regeneration utility. It is not invoked by the
canonical notebook during normal analysis.

## Provenance rule

Do not substitute a locally acquired or regenerated file for a governed
analysis input without running the repository validation and provenance checks.
Unsupported observations, structural missingness and observed zeroes have
distinct meanings and must not be collapsed during regeneration.

See `RP1_Project/docs/external_data_contract.md` for the normative data-class
and authority rules.
